# ADR-010: Hybrid VLM + Classical CV for Graph Structure Extraction

## Status
Accepted — confirmed directly by the project owner, following a live empirical test.

## Context
The project owner uses node/edge graph diagrams heavily (CS algorithms coursework — trees, weighted graphs, network diagrams) and asked whether VisionLearn could extract queryable graph structure (which nodes connect to which, and edge weights), not just a one-sentence description.

Before building anything, this was tested empirically against the existing VLM-only pipeline ([ADR-004](./ADR-004-vlm-first-pipeline.md), [ADR-009](./ADR-009-openai-as-active-vlm-provider.md)):

- A synthetic 5-node, 6-edge graph with no crossing lines: the VLM (`gpt-4o`) correctly described it.
- A synthetic 7-node, 12-edge graph with 6 crossing-line pairs: single-pass accuracy was 50-75% (varied across 3 independent runs, averaging ~69%). Critically, the errors were not random noise — repeated runs converged on the *same wrong* edge attribution for the same crossing patterns (e.g., edge A-E was misattributed as B-E in 2 of 3 independent runs). Majority-voting across the 3 runs only recovered 75% accuracy, because the systematic bias sometimes wins the majority vote in the wrong direction.

This ruled out both "ask the VLM directly" and "ask the VLM multiple times and vote" as reliable approaches — the failure is a consistent perceptual bias when visually tracing a specific line through a crossing, not randomness that more sampling fixes.

A classical computer-vision approach was then prototyped and tested against the same 12-edge crossing graph: rather than asking anything to *trace* a line, test every candidate node pair directly by sampling pixels along the straight path between the two node centers and checking what fraction land on a drawn line. This scored **100% topology accuracy** (12/12 edges, zero false positives) — because it never has to disambiguate which fragment belongs to which line; crossings elsewhere in the image are irrelevant to a pixel-occupancy test along a known path.

## Decision
Extract graph structure via a **hybrid pipeline**, splitting the task along each system's actual strength:

1. **The VLM** (`ClaudeVLMAnalyzer` / `OpenAIVLMAnalyzer`, unchanged provider selection per ADR-009) locates node positions (label, center, approximate radius) and weight-label positions/values, for any object it classifies as a node/edge graph diagram. This is bounding-box localization and text reading — tasks vision models are reliably good at, and this pipeline still relies on them for exactly that.
2. **Classical CV** (`backend/app/services/graph_topology.py`) takes those node positions and determines actual edge connectivity by pixel-sampling between every candidate pair in a generalized (Canny-based, color-agnostic) edge map — the one task empirically measured to fail when asked of the vision model.
3. Each detected edge is assigned the nearest weight label by geometric proximity to the edge's midpoint.

The VLM is explicitly instructed **not** to attempt determining connectivity itself (`prompts/analysis.v2.md`) — only to report where nodes and weight labels are. This isn't a redundant safety net; asking it to also guess at edges would reintroduce the exact failure mode this ADR exists to avoid, for zero benefit (its guess is discarded either way).

## Rationale
- **Evidence-driven, not speculative.** Every claim above was measured on live API calls before writing production code, not assumed. The specific numbers (100% vs. ~69-75%) are what justify the added complexity of a second pipeline stage and a new dependency.
- **Plays to each system's strength.** Vision-language models are good at "what is this and where is it," not at "trace this specific line through a crowd of crossing lines." Classical geometric algorithms are the reverse: they can't tell you a node's label, but a straight-line pixel-occupancy test is exact and unaffected by how many other lines cross elsewhere.
- **Fails safely.** If the CV step errors for any reason (malformed node data, an undecodable image), `vlm_output.py` catches it and leaves `graph_structure: null` rather than failing the whole analysis (docs/ARCHITECTURE.md §6 "never crash") — the object still gets its ordinary type/summary/confidence fields.
- **New prompt version, not an in-place edit.** Per `docs/PROMPTS.md`'s versioning convention, this ships as `analysis.v2.md` (not a rewritten `v1`), so the change is independently rollback-able from the code that consumes it.

## Alternatives Considered
- **Majority-voting across repeated VLM calls.** Tested directly (see Context) — only reached 75% because the model's crossing-edge errors are a consistent bias, not random noise. Rejected: doesn't solve the actual failure mode, and costs 3x+ the API spend for a partial improvement.
- **VLM-only with better prompting** (e.g., "trace carefully," "double-check crossings"). Not separately tested as its own path, but the majority-voting result already demonstrates the failure is a perceptual bias in how the model visually resolves crossings, not an instruction-following gap — no prompt wording changes what pixels the model's attention mechanism resolves to at an intersection.
- **Pure classical CV, no VLM involvement** (detect node shapes and text via CV/OCR too). Rejected for now: reliable generic node-shape detection (circles vs. boxes vs. plain text labels, arbitrary drawing styles) and OCR of arbitrary node labels is a much harder, less certain CV problem than the one actually being solved here (straight-line pixel occupancy between two *known* points). Leaning on the VLM for localization avoids re-solving a hard problem the VLM already does reliably.
- **Fixed-color-threshold CV** (the first prototype, which scored 100% on the synthetic test image). Rejected as the shipped implementation: it was tuned to one digitally-rendered image's exact colors and wouldn't generalize to a real photo of a lecture slide or whiteboard (lighting variation, arbitrary colors). The shipped version uses Canny edge detection on grayscale instead — re-validated separately at 100% on the same test graph before being wired into the pipeline (see `graph_topology.py`'s module docstring).

## Consequences
- New runtime dependency: `opencv-python-headless` + `numpy` (`backend/pyproject.toml`).
- `SlideObject` gains an optional `graph_structure: GraphStructure | None` field (`nodes: list[str]`, `edges: list[{node_a, node_b, weight}]`) — see `docs/API_CONTRACT.md` §2.
- Classical edge detection can still be fooled by non-edge lines passing between two nodes that happen to align (e.g., a table gridline, an unrelated arrow) — this is a lower-probability failure mode than the crossing-edge problem it replaces, but not impossible; not exhaustively tested against adversarial layouts.

### Live end-to-end testing found two more real bugs, both fixed before shipping

Live testing against the real OpenAI API (not just synthetic unit tests) surfaced two further failure modes the synthetic tests didn't exercise, because synthetic tests used exact or lightly-perturbed node math rather than a real model's actual output distribution:

1. **VLM node-position error is large enough to break naive pixel-sampling outright.** Measured error in an 800x500 image ranged from ~40-60px up to ~160px call-to-call (not a fixed bias — it varies). `graph_topology.py` now refines every VLM-reported node position before any connectivity test: `cv2.HoughCircles` detects circles once over the *whole* image (not a small window around each guess — a windowed search was tried first and rejected, since sizing the window as a multiple of the reported radius caps how much error it can correct, and live testing exceeded that cap). Each VLM guess is then matched to its best detected circle via a combined score — pixel distance plus a penalty per Hough confidence-rank step — resolved nearest-score-first, unique per node and per circle. Distance alone was tried first and failed a unit test: an unrelated real circle elsewhere in the image (not even in the current node list) was closer to a badly-off guess than that guess's own true circle. Confidence-rank-only ordering was also tried and failed differently: a strong, cleanly-detected circle could steal a different node's slot purely by being processed first, even when that node's own true circle was a near-perfect (near-zero-distance) match. The combined score fixes both: an exact/near-exact distance match always wins regardless of rank, while rank still breaks the genuinely ambiguous cases distance alone gets wrong. Re-verified via multiple fresh (uncached) live API calls against the original test image — topology now consistently 10/10 across every rerun.
2. **Weight-label assignment can pick the wrong edge when the VLM's own label position is noisy**, not just when two edges share a midpoint (the collision case already handled by nearest-first-unique assignment). Live testing found a case where a label's reported position was genuinely closer to the *wrong* edge's midpoint than to its true edge's — the assignment code correctly picked the nearest edge to the label's reported position, but that position was itself off enough to point at the wrong edge. This is a real, observed limitation, not yet fully mitigated: unlike the node-position problem, there's no equivalent of Hough circle detection for a text label (nothing to snap "10" back to its true position from). Topology (the primary problem this ADR solves) is unaffected — this is specific to weight *values*, a secondary enrichment on top of the connectivity structure.

**Current status after live verification:** topology (nodes + edges) is reliably correct across repeated fresh live-API test runs on the original coursework-style test image. Weight-label values are usually correct but can occasionally be misassigned when the VLM's own reported label position is inaccurate — treat edge weights as best-effort, and topology (which node connects to which) as the validated, reliable part of this feature.

### Real coursework material (photos, busy slides) required a second architectural change: two-pass localization

Testing against the project owner's actual coursework material (not just the synthetic renders above) surfaced a deeper problem than the position-error/weight-collision bugs already fixed. Two real images were tested:

1. A clean, digitally-rendered "Exhaustive Search" slide with a small 6-node unweighted graph in the corner of a bullet-point-heavy slide.
2. A JPEG photo of a "Floyd's Algorithm" slide with a 4-node directed, weighted graph including two curved bidirectional edges between the same node pair.

Both initially failed completely (0 edges), for reasons neither prior fix addressed:

- The VLM's node-position accuracy, when asked for full-slide-normalized coordinates, degraded far beyond the ~40-160px already documented — badly enough to report a position *outside the diagram's own bounding box entirely* when the diagram was a small fraction of a busy slide.
- Small node icons (~15px radius) were both unreliably detected by Hough and easily confused with *other* circular elements elsewhere on the same slide (bullet-point markers in one case) that a whole-image circle search has no way to rule out.

**Fix: a second, focused VLM pass.** The first analysis pass now only signals "this object is a graph" — its own `graph_nodes`/`graph_weight_labels` are discarded. `crop_object_region()` (`graph_topology.py`) crops the original image down to just that object's `bounding_box`, trims tightly to the actual drawn content (largest connected component after a small dilation — chosen over a raw non-white-pixel bounding box because that caught unrelated stray marks elsewhere in the padded crop, like leftover title text), and upscales small crops. A second VLM call (`prompts/graph_localization.v1.md`, see `docs/PROMPTS.md` §2b) then locates nodes/weights *within that clean crop only* — a far easier task with nothing else in frame to compete for the model's spatial attention or to be mistaken for a node. Confirmed via a live, fresh API call through the actual wired application (not just standalone scripts): the Exhaustive Search slide now returns all 7 edges correctly, zero errors.

Two more CV bugs surfaced and were fixed once localization was solid enough to expose them:
- **Canny's centerline gap.** Canny marks a line's top/bottom boundary, not its filled interior; for a line a few pixels thick (common after the localization crop's upscaling), that leaves a real gap exactly along the geometric centerline connectivity sampling sits on — a genuine edge scored 0.00 because every sample landed in that gap. Fixed by widening the edge-map dilation kernel (5x5, later 7x7 to handle a lower-contrast real photo) — enough to close the gap, still far short of bridging genuinely separate crossing lines.
- **Circle radius tolerance.** The VLM's radius estimate was 2x too large on the JPEG photo, shifting `_detect_circles`'s entire search band away from the true circle size. Widened from 0.5x-1.8x to 0.3x-2.5x tolerance.

### Curved and directed edges

The project owner's real use case includes directed graphs with curved edges (e.g. two separate arcs for a bidirectional pair, each with its own weight) — not just straight undirected lines. This required extending the connectivity test itself, in two ways that both needed to preserve the crossing-immunity property that is this ADR's original point:

- **A family of curved candidate paths, not only the straight line.** `_find_edge_instances` tests a fixed set of quadratic-Bezier "bulge" offsets (perpendicular to the straight line, from -40% to +40% of the distance) between every node pair, not just bulge=0. This is still never *tracing* — each candidate is a specific, fully-determined path tested for pixel occupancy, the same principle as the original straight-line test. Needed even for lines that look straight: live testing measured ~5-9px of real perpendicular deviation on a "straight" connector in the JPEG photo. Adjacent qualifying bulges are clustered as one physical curve, so a genuinely bidirectional pair (two arcs) correctly yields two separate `GraphEdge` entries.
- **Occupancy fraction alone isn't a safe connectivity signal once curves are allowed.** The noise-robustness regression test (12-edge crossing graph, ±35px simulated position noise) caught two new false positives directly attributable to curve tolerance: a candidate curve between two non-adjacent nodes scored a high *raw* occupancy fraction by skimming past several different real lines with small gaps between them — never following one continuous stroke. Fixed with a longest-contiguous-run metric (`_longest_run_fraction`, small gaps bridged, real breaks are not) used in place of raw occupancy fraction: a genuine stroke gives one long run, several coincidentally-skimmed strokes give several short ones. A second false positive (a curved "shortcut" riding through a third node, the curved analogue of the earlier straight-line collinear-chain bug) was fixed by checking every sampled point on the *actual candidate curve* — not just the straight segment — against every other node's circle, for every tested bulge, not only bulge=0.

**Direction detection** (`_detect_direction`) went through three iterations, each driven by a concrete measured failure rather than guesswork:

1. **Local ink density near each endpoint** (an arrowhead is a filled shape wider than the line, so it should locally raise density). Rejected: an *absolute* density threshold falsely flagged every edge in an undirected test graph as `"bidirectional"`, because a plain line's own thickness already fills a meaningful fraction of any nearby window (measured at ~0.6-0.8 density with no arrowhead present at all).
2. **Density *ratio* between the two ends** (same signal, compared relatively instead of absolutely). Fixed the false-`"bidirectional"` problem and correctly separated a one-sided arrow from a plain line, but by construction can't tell "both ends dense" (a genuine bidirectional edge) from "neither end dense" (a plain line) — both give a ratio near 1. Bidirectional edges reported as `"undirected"` under this version.
3. **Perpendicular ink-width profile, moving away from each node** (`_perpendicular_ink_width` + `_has_arrowhead`) — the shipped approach. An arrowhead is a filled triangle: wide near the node, narrowing to the connecting line's constant width a short distance further out. A plain line has no such narrowing anywhere. This directly encodes the actual geometric shape of an arrowhead rather than a density proxy for it, and correctly detects `"bidirectional"` (both ends narrow) alongside the one-sided cases — confirmed against all four synthetic cases (undirected, `a_to_b`, `b_to_a`, bidirectional).

Getting version 3 right took two rounds of live calibration:
- **Where to start sampling.** The connectivity test's own margin (`radius + 6px`) already lands past a typical arrowhead's whole extent — measured directly: a real arrowhead's profile became indistinguishable from a plain line's when sampled from that margin, because a real arrowhead's tip touches the node boundary with its wider base only a fraction of a radius further out. Anchoring instead to distance-from-the-node's-own-center (as a multiple of its radius) fixed this — but even then, up to ~1.1x radius the profile is dominated by the node's own circle outline regardless of arrowhead presence; the real signal only emerged from ~1.15x-1.7x radius.
- **A single near-sample isn't enough.** Taking the *max* of the near samples caught real arrowheads but produced a live false positive: a plain line on a real photo showed one transient width spike at exactly the closest sample (1.15x radius) — evidently the node's circle-boundary echo lingers slightly further for that image's specific rendering — that a max-based check couldn't distinguish from a genuine arrowhead. Requiring at least two of the three *non-closest* near samples (1.3x, 1.5x, 1.7x) to independently clear the ratio threshold fixed it: a real arrowhead's width stays elevated across multiple samples (a sustained taper), while the false-positive circle-echo was a single-sample blip.

**Current status on real coursework material:**
- **Clean digital slides:** validated fully correct (7/7 topology, zero errors, correct `"undirected"` direction on every edge) via multiple live, fresh calls through the actual running application — including after the direction-detection rework, confirming the false-positive fix holds live, not just in the calibration script.
- **Topology on photos with curved/directed edges (the harder case):** substantially improved (0/5 → 3/5 unique edges on the Floyd's Algorithm test photo, correct weight on every edge found) but not fully solved — the two remaining edges both involve the most pronounced bidirectional arcs, right at the edge of the connectivity threshold on this specific low-contrast JPEG.
- **Direction on that same hard photo:** correctly identifies at least one real directed edge (`a_to_b`) on fixed node positions; the other two found edges default to `"undirected"` rather than guessing — a real, direction-bearing edge going undetected is a coarser answer, not a wrong one, unlike a plain edge being mislabeled `"bidirectional"` (the version-3 regression this rework fixed).
- Treat topology on clean digital slides as reliable; treat photos of hand-drawn or heavily curved directed graphs as best-effort, with weights and direction as a secondary, occasionally-incomplete-but-not-wrong layer on top either way.
